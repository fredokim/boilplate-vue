# vue 보일러플레이트를 공용 백엔드에 연동

백엔드는 `fredokim/boilplate-server`에 있다. react 보일러플레이트가 이미
연동되어 있고, 이 문서는 vue를 같은 서버에 붙이는 작업이다.

아래 단계는 각각 독립적으로 실행 가능한 프롬프트다. 한 번에 하나씩 실행하고,
완료 조건을 만족한 뒤 다음으로 넘어간다.

---

## 배경 — 이미 있는 것과 없는 것

**있는 것.** 이 저장소에는 이미 타입이 잡힌 HTTP 계층이 있다.

- `src/core/api/http-client.ts` — axios 기반 `TypedHttpClient`. 요청
  인터셉터가 access token을 `Authorization` 헤더에 붙이고, 응답을 DTO로
  검증하며, 실패를 `TypedApiError`로 바꾼다.
- `src/core/api/index.ts`가 `apiClient` 인스턴스를 내보낸다.
- `src/core/auth/token-storage.ts` — access token 보관.
- 각 모듈의 api 파일이 이미 `/api/...` 경로를 쓴다. 예를 들어
  `modules/auth/api/auth.api.ts`의 `basePath`는 `"/api/auth"`다.

즉 경로와 클라이언트는 이미 서버를 향하고 있다. 지금 그 요청을 받는 것은
MSW다.

**없는 것.**

1. **개발 프록시.** `vite.config.ts`에 `server.proxy` 설정이 없다. react
   쪽에는 있다.
2. **데이터 모드 스위치.** mock과 서버를 고르는 지점이 없다. react의
   `src/core/config/dataMode.ts`가 하는 일이다.
3. **401 갱신.** `http-client.ts`에 401이나 refresh를 다루는 코드가 없다.
   access token이 만료되면 세션이 그냥 끝난다.
4. **실시간 서버 트랜스포트.** `realtime/`에 `mockChatTransport.ts`와
   `mockTransport.ts`만 있다. react에는 `serverChatTransport.ts`와
   `serverTopologySource.ts`가 있다.

---

## 계약 불일치 — 먼저 알고 시작한다

vue의 DTO는 MSW mock에 맞춰 쓰였고, 서버가 실제로 보내는 것과 다르다.
이것을 모르고 붙이면 로그인은 되는데 세션 복원이 실패하는 식으로 어긋난다.

| | vue가 기대하는 것 | 서버가 보내는 것 |
| --- | --- | --- |
| 사용자 권한 | `roles: string[]` | `permissions: string[]` |
| 로그인 응답 | `{ user, accessToken, refreshToken? }` | `{ accessToken, user }` |
| 세션 응답 | `AuthSessionDto` (accessToken 포함) | `{ user }` 만 |
| 갱신 요청 | 본문에 `{ refreshToken }` | 본문 없음. HttpOnly 쿠키에서 읽음 |
| **봉투** | `{ status: "SUCCESS", code?, message?, data }` | `{ success, data }` / `{ success, error: { code, message } }` |

마지막 줄은 이 표를 처음 쓸 때 빠져 있었고, 실제로는 **가장 큰 불일치**다.
봉투에 `status` 필드가 없으므로 서버의 어떤 응답도 검증을 통과하지 못한다.
즉 DTO 네 개를 고쳐도 그 전에 모든 호출이 실패한다.

마지막 줄이 특히 중요하다. 서버는 refresh token을 **응답 본문에 절대 넣지
않는다.** 쿠키로만 오간다. vue의 `refreshSession(refreshToken)`은 서버가
읽지 않는 값을 보내고 있다.

`AuthSessionDto`를 서버에 맞추는 방향으로 고친다. 반대 방향은 안 된다.
서버는 세 프론트가 공유하므로 한 프론트를 위해 계약을 바꿀 수 없다.

---

## 이 작업의 범위

포함한다: 프록시, 데이터 모드 스위치, 인증 흐름 정렬, 401 단일 비행 갱신,
실시간 서버 트랜스포트, 계약 테스트.

포함하지 않는다: MSW 제거(mock 모드는 유지한다), 소셜 로그인
(`social/` 아래 코드는 서버에 대응 엔드포인트가 없다), 배포.

## 단계 3-1 — 프록시를 붙이고 서버가 살아 있는지 확인한다

지시:

1. `vite.config.ts`에 `server.proxy`를 추가한다. react의
   `vite.config.ts`를 본보기로 삼되 그대로 베끼지 말고, 이 저장소의 포트와
   구조에 맞춘다. `ws: true`를 반드시 포함한다. 게이트웨이가 둘 있다.
2. 대상은 `process.env.VITE_API_TARGET ?? "http://127.0.0.1:3001"`로 둔다.
3. 백엔드를 띄우고 개발 서버에서 `/api/health/live`를 호출해 본다.

완료 조건:

- 브라우저에서 `/api/health/live`가 JSON을 돌려준다. HTML이 오면 프록시가
  아니라 SPA fallback에 걸린 것이다.
- 이 단계에서는 애플리케이션 코드를 바꾸지 않는다.

---

## 단계 3-2 — 데이터 모드 스위치를 만든다

지시:

1. `src/core/config/dataMode.ts`를 만든다. react의 같은 파일이 본보기다.
   `VITE_DATA_MODE`가 `mock`과 `server` 두 값을 갖고, 오타는 조용히 mock으로
   떨어지지 않고 예외를 던진다.
2. 프로덕션 빌드에서 mock 모드를 거부한다. mock 위에서 도는 프로덕션
   번들은 화면상 멀쩡해 보이면서 전부 지어낸 데이터를 보여준다.
3. ~~MSW 시작 지점이 이 스위치를 따르게 한다.~~ **이 저장소에는 브라우저용
   MSW가 없다.** `setupWorker` 호출도 `public/`의 worker 파일도 없고, MSW는
   테스트(`msw/node`)와 Storybook 스토리 하나에서만 쓰인다. 브라우저에서
   mock 모드가 뜻하는 것은 화면이 스스로 제공하는 데모 데이터, 구체적으로는
   로그인 화면의 "Use demo session" 버튼이다.

   따라서 스위치가 가려야 하는 것은 worker가 아니라 **그 버튼**이다. 서버
   모드에서 데모 세션을 만들면 백엔드가 발급한 적 없는 토큰을 들게 되고,
   첫 인증 요청이 실패한다. 그건 데모가 아니라 고장난 로그인처럼 보인다.

4. 가드를 `main.ts`에서 평가되게 한다. 지연 로드되는 화면에서만 import하면
   잘못된 빌드가 일단 부팅한 뒤 나중에 터진다.
5. `package.json`에 `dev:server-mode` 스크립트를 추가한다.

완료 조건:

- `npm run dev`는 지금과 똑같이 동작한다.
- 서버 모드로 빌드한 결과물에서 "Use demo session" 버튼이 사라진다.
- mock 모드로 **빌드한 결과물을 실행하면** 앱이 부팅하지 않는다. 빌드
   자체는 성공한다. 가드는 런타임에 던지므로 `vite build`의 종료 코드로는
   확인할 수 없다. 이 점을 착각하면 검증하지 않고 통과시키게 된다.

## 단계 3-3 — 인증 DTO를 서버 계약에 맞춘다

위 표의 네 줄을 실제로 고치는 단계다.

지시:

1. `AuthUserDto`의 `roles`를 `permissions`로 바꾸고, 이 필드를 읽는 곳을
   모두 찾아 고친다. 권한 검사 로직이 있으면 함께 본다.
2. 로그인 응답 DTO를 `{ accessToken, user }`로 맞춘다.
3. 세션 응답 DTO를 `{ user }`로 맞춘다. 세션 조회는 access token을 주지
   않는다.
4. `refreshSession`에서 본문을 없앤다. 쿠키로만 동작한다. axios가 쿠키를
   보내도록 `withCredentials`가 필요한지 확인한다. 프록시를 쓰면 동일
   출처이므로 필요 없을 수 있다. 추측하지 말고 실제로 확인한다.
5. 서버가 인증 실패에 쓰는 코드는 `AUTH_REQUIRED`다. 이 문자열로 분기하는
   지점을 만든다.

완료 조건:

- `npm run typecheck`가 통과한다. `roles` 사용처가 남아 있으면 여기서 걸린다.
- 서버 모드에서 로그인이 성공하고 사용자 이름이 화면에 나온다.
- 새로고침해도 세션이 유지된다.

---

## 단계 3-4 — 401 갱신을 배선한다

지시:

1. `http-client.ts`에 응답 인터셉터를 추가한다. 401이고 아직 재시도하지
   않은 요청이면 한 번만 갱신하고 한 번만 재시도한다.
2. **갱신은 단일 비행이어야 한다.** 서버의 refresh token은 회전하며, 이미
   사용된 token이 다시 제시되면 재사용으로 판단해 **세션 패밀리 전체를
   폐기한다.** 화면 로드 시 요청 다섯 개가 동시에 401을 받고 각각 갱신을
   부르면, 첫 번째가 회전시킨 뒤 나머지 넷이 이미 쓴 token을 제시하고,
   서버는 그것을 공격으로 읽는다. 즉 병렬 갱신은 사용자를 로그아웃시킨다.
   react의 `src/core/api/refreshSingleFlight.ts`가 이 문제를 푼 코드다.
3. 갱신 요청 자체는 재시도 대상에서 제외한다. 그러지 않으면 갱신이 401일 때
   자기 자신의 진행 중 프라미스를 기다리며 멈춘다.
4. 갱신이 실패하면 로그아웃한다. 서버가 더 이상 인정하지 않는 토큰을 들고
   "로그인된 것처럼" 남아 있으면 안 된다.

완료 조건:

- 동시에 401이 여러 건 발생하는 화면에서 `/api/auth/refresh` 요청이
  **정확히 한 번** 발생하는 것을 네트워크 패널로 확인한다. 여러 번이면
  단일 비행이 동작하지 않는 것이다.
- 갱신 후 원래 요청들이 재시도되어 성공한다.

## 단계 3-5 — 실시간 트랜스포트를 붙인다

지시:

1. `realtime/`에 서버 트랜스포트를 만든다. react의
   `serverChatTransport.ts`와 `serverTopologySource.ts`가 프로토콜의
   본보기다. 핸드셰이크는 쿼리스트링의 토큰으로 인증하고, 실패하면 서버가
   4401로 닫는다.
2. **전송은 HTTP, 수신은 소켓이다.** 채팅 메시지 전송을 소켓으로 옮기지
   않는다. 권한 검사와 멱등성 키와 rate limit이 HTTP 경로에 있고, 소켓에
   같은 것을 다시 구현하면 "이 사람이 쓸 수 있는가"에 대한 답이 두 벌
   생긴다.
3. 재연결은 마지막 sequence부터 replay한다. 보존 범위를 벗어나면 서버가
   resync를 지시한다.
4. **스위치가 실제로 트랜스포트를 고르게 한다.** react에서 이 부분이
   실패한 적이 있다. 서버 트랜스포트를 만들고 단위 테스트까지 했지만
   배선 지점이 mock을 하드코딩하고 있어서, 서버 모드인데 화면에는
   "Connected"라고 표시되며 지어낸 메시지가 흐르고 있었다.

완료 조건:

- 서버 모드에서 채팅 화면이 **데이터베이스에 있는 메시지**를 보여준다.
  생성된 것처럼 보이는 메시지가 나오면 여전히 mock이다.
- 브라우저를 열어둔 채 HTTP로 메시지를 하나 보내면 새로고침 없이 도착한다.
- 토폴로지 이벤트를 하나 발행하면 화면의 카운터가 바뀐다.

## 단계 3-6 — 계약 테스트를 추가한다

지시:

1. 백엔드의 `openapi.json`을 `contracts/openapi.json`으로 가져온다.
   react가 같은 방식을 쓴다.
2. 프론트가 호출하는 URL을 소스에서 추출해 스펙과 대조하는 테스트를 만든다.
   손으로 목록을 적지 않는다. react에서 그렇게 했다가 서버가 구현한 적 없는
   엔드포인트를 놓쳤다. 목록이 구현된 것만 담고 있어서 자기 자신과만
   일치했다.
3. 경로 파라미터 이름은 비교에서 제외한다. 클라이언트와 서버가 각자 짓는다.
4. `npm run contract:sync`로 스펙을 갱신할 수 있게 한다.

완료 조건:

- 스펙에서 임의의 경로 하나를 지우면 테스트가 실패하고, 되돌리면 통과한다.
  **두 경우를 모두 실행해 확인한다.** 확인하지 않은 게이트는 게이트가 아니다.
- `check:ci`에 포함된다.

## 단계 3-7 — 문서와 포트폴리오

지시:

1. `DEPLOYMENT.md`를 만든다. 쿠키가 `sameSite: lax`이므로 브라우저가 단일
   출처를 봐야 하고, 그래서 프록시가 필요하다는 점을 적는다. 백엔드
   저장소의 같은 문서가 본보기다.
2. README에 서버 모드 실행 방법을 적는다.
3. 포트폴리오에 vue도 실서버에 연동되었음을 반영한다. 현재 포트폴리오는
   "백엔드는 React 저장소에만 있습니다"라고 적혀 있고, 이 작업이 끝나면
   그 문장이 사실과 달라진다.

완료 조건:

- `npm run check:ci`가 통과한다.
- 포트폴리오를 다시 굽고 아티팩트를 갱신한다.
